## 1. 한 줄 요약

**inni**는 교사가 핸드폰으로 바코드를 찍고 바로 출고·반납·위치 이동을 끝내고, PC에서는 대장·실사·라벨 인쇄·AI 도움을 받는 **학교 현장용 기자재/비품/소모품/실(room) 통합 관리 웹서비스**다.
---

## 2. 왜 Part-DB를 참고하되, 그대로 만들지 않는가

Part-DB는 훌륭한 재고 개념을 갖고 있다.

| Part-DB 개념 | 학교 서비스로 옮기는 방식 |
|--------------|---------------------------|
| Part (품목 종류) | **품목(Item)** — 동일 규격의 비품·소모품·부품 |
| Stock / Lot | **재고 로트** — 어느 실/선반에 몇 개 |
| Category | **분류 트리** — 학과·교과·용도 기준 |
| Storage location | **위치 계층** — 건물 > 실 > 선반 > 칸 |
| Label profile | **라벨 템플릿** — 바코드/QR + 학교 양식 |
| Permissions | **역할** — 관리자 / 담당교사 / 학생(제한) |
| Event log | **이력** — 누가 언제 무엇을 출고·이동·폐기 |

다만 Part-DB는 **전자부품 연구실/메이커스페이스**에 최적화되어 있다. 마이스터고는 다음이 다르다.

- **개체 단위 자산**이 많다 (CNC 1대, 오실로스코프 3대처럼 시리얼·관리번호가 있는 장비)
- **대여/반납**이 일상이다 (수업·프로젝트·야간자율)
- **실(room)** 자체가 관리 단위다 (실습실 담당, 안전점검, 배치도)
- **에듀파인 자산번호** 등 공적 식별자와 병행해야 할 수 있다
- 사용자(교사·학생)의 IT 숙련도가 제각각 → **3탭 안에 끝나야** 한다
- 한국어 UI, 학교 용어, 학사 일정(학기·방학·실사 기간)이 필요하다

→ Part-DB의 **데이터 모델 철학**은 가져오고, **학교 워크플로·UX**는 새로 설계한다.

## 3. 문제 정의

### 3.1 현장 Pain

1. 엑셀·종이 대장으로 관리 → 실시간 위치/재고를 모름
2. “그 드릴 어디 갔어?” → 찾느라 수업 준비 시간 소모
3. 소모품(드릴비트, 전선, 납땜)은 누가 가져갔는지 안 남음
4. 학기 말 실사는 수기 체크 → 누락·중복
5. 바코드가 있어도 스캐너·전용 SW가 없으면 유명무실
6. 새 담당교사가 오면 인수인계가 문서·구두에 의존

### 3.2 목표 사용자

| 페르소나 | 니즈 | 주로 쓰는 기기 |
|----------|------|----------------|
| **실습실 담당교사** | 등록·출고·실사·라벨·보고서 | PC + 폰 |
| **일반 교과교사** | 수업 전 장비 대여·반납, 실별 목록 열람 | 폰 위주 |
| **학과장/부장** | 현황·부족·폐기 후보 파악 | PC |
| **학생 (후순위)** | 내 대여 조회, 시설 고장 신고 | 폰 |
| **행정/자산 담당** | 관리번호·구입정보·폐기 이력, 에듀파인 동기화 | PC |

### 3.3 성공 기준 (초기)

- 담당교사가 **신규 비품 등록 → 라벨 출력 → 부착**까지 5분 이내
- 교사가 폰으로 **스캔 → 출고/반납**을 30초 이내
- “이 장비 어디 있지?”를 **검색/스캔 1회로 위치 확인**
- **실을 열어 그 실의 장비·비품 목록**을 바로 훑을 수 있음
- 학기 말 실사: 실별 체크리스트 + 스캔으로 **미확인 목록 자동 생성**
- 첫 사용 교사도 **튜토리얼 없이 핵심 3기능**(찾기 / 출고 / 등록) 가능
- 수천 품목·수십 실에서도 검색·실별 목록이 **답답하지 않음** (목표: 목록 첫 화면 1초대)

## 4. 제품 원칙 (비협상)

1. **모바일 퍼스트 액션, PC 퍼스트 관리**  
   - 폰: 스캔·출고·반납·빠른 검색  
   - PC: 대량 등록, 라벨 배치 인쇄, 실사, 설정, AI 정리
2. **스캔이 기본 입력** — 타이핑은 최후 수단
3. **용어는 학교말** — Part/Lot 대신 품목·재고·실·선반·대여
4. **역할별 화면을 줄인다** — 학생·일반교사는 “내 대여 / 스캔”만 보여도 됨
5. **빈 화면을 허용하지 않는다** — 온보딩 샘플 데이터·가이드 카드
6. **오프라인 완전 지원은 v1 비목표** — 다만 스캔 UX는 네트워크 끊김 시 명확히 안내
7. **개발 전 기획을 충분히** — 본 PRD는 합의용 문서이며 구현 범위는 단계적으로 확정

## 5. 핵심 도메인 모델

### 5.1 자산 유형 (Asset Type)

한 시스템 안에서 성격이 다른 물건을 **유형으로 구분**한다.

| 유형 | 설명 | 재고 방식 | 예시 |
|------|------|-----------|------|
| **기자재/장비 (Equipment)** | 개체 식별 필요 | **1물품 = 1레코드** (시리얼/관리번호) | CNC, 오실로스코프, 노트북 |
| **비품 (Fixture)** | 동일 규격 다수, 개체 추적 약함 | 수량 + 위치 | 의자, 책상, 공구세트 |
| **소모품 (Consumable)** | 쓰면 줄어듦 | 수량 + 최소재고 알림 | 드릴비트, 전선, 납땜, A4 |
| **부품/재료 (Part)** | Part-DB식 부품 | 수량 + 다위치 | 저항, 볼트, 베어링 |

> UX상 사용자는 “장비 추가 / 소모품 추가”처럼 고르고, 내부적으로 타입별 필드가 달라진다.

### 5.2 위치 계층 (Location)

```
학교
 └─ 건물/동
     └─ 실(Room)          ← 핵심 단위 (실습실, 공구실, 창고)
         └─ 구역(Zone)    ← 선택 (A존, 용접구역)
             └─ 보관함(Storage)  ← 선반/서랍/캐비닛
                 └─ 칸(Bin)      ← 선택
```

**실(Room)**은 단순 위치가 아니라:

- 담당교사
- 학과/과정
- 안전수칙·점검 체크리스트(후순위)
- 배치된 고정 장비 목록
- 출입/사용 메모

를 가질 수 있는 **1급 엔티티**다.

### 5.3 품목 vs 개체

- **품목(Catalog Item)**: “Fluke 87V 멀티미터”라는 종류
- **개체(Asset Instance)**: 그 중 관리번호 `전장-2024-017`인 **그 한 대**
- 소모품/부품은 개체를 만들지 않고 **품목 + 위치별 수량**만 둔다

### 5.4 이동·상태 머신 (장비)

```
보관중 → 대여중 → 보관중
보관중 → 수리중 → 보관중 / 폐기예정
보관중 → 이동중(실 간) → 보관중
임의 → 분실신고 → (회수) 보관중 / 폐기
폐기예정 → 폐기완료
```

모든 상태 변경은 **이력**에 남는다 (누가, 언제, 왜, from→to).

### 5.5 식별자

| 식별자 | 용도 |
|--------|------|
| 내부 ID | 시스템 고유 |
| 관리번호 | 학교 자체 채번 (라벨에 인쇄) |
| 바코드/QR 코드값 | 스캔용 (관리번호와 동일하거나 별도) |
| 시리얼번호 | 제조사 S/N |
| 에듀파인/자산번호 | **옵션 필드** (수동 입력 → 이후 파일 동기화) |
| 태그 | 자유 분류 (#용접 #1학년프로젝트) |

## 6. 주요 기능 요구사항

우선순위: **P0** = MVP 필수 / **P1** = 초기 확장 / **P2** = 이후

### 6.1 인증·권한 — P0

- Firebase Authentication (Google 로그인 우선)
- 학교 도메인 제한 옵션 (예: `@school.go.kr`만 허용) — 설정 가능
- 역할:
  - **Owner/관리자**: 학교 설정, 사용자 승인, 전체 권한
  - **Manager/담당교사**: 등록·수정·실사·라벨·폐기 처리
  - **Teacher/일반교사**: 검색·대여·반납·본인 이력
  - **Student/학생**(옵션): 대여 신청·본인 대여 조회 (학교별 on/off)
- 초대 링크 또는 관리자 승인 후 접근
- 모든 쓰기 작업에 userId 기록

### 6.2 찾기 (Search) — P0 ★최중요

- 통합 검색: 이름, 관리번호, 시리얼, 태그, 위치명
- **카메라 바코드/QR 스캔** → 상세 즉시
- 필터: 유형 / 실 / 상태 / 담당 / 재고부족
- 최근 본 항목, 즐겨찾기
- “내 담당 실” 바로가기

### 6.3 등록·수정 — P0

- 빠른 등록 폼 (필수 필드 최소화)
  - 이름, 유형, 위치(실), 수량 또는 관리번호
- 사진 촬영 첨부 (폰 카메라)
- 엑셀/CSV 일괄 등록 (PC) — P0 후반 또는 P1
- 분류 트리 관리
- 최소 재고(소모품) 설정

### 6.4 대여·반납·출고 — P0

- 스캔 후 **대여** (대상: 교사/학생, 예정 반납일, 용도)
- 스캔 후 **반납** (상태 이상 시 메모·사진)
- 소모품 **사용 출고** (수량 차감, 사유: 수업/프로젝트)
- 일괄 출고 (프로젝트 키트) — P1
- 연체 알림 (푸시/이메일 — P1)

### 6.5 이동·실 관리 — P0 ★장소별 열람 강조

- 실 목록·담당자·메모
- 실 → 실 이동 (스캔 또는 목록 선택)
- **실 상세 = 그 장소의 장비·비품·소모품 목록** (필터: 유형/상태/대여가능)
- 보관함(선반) 단위로도 목록 드릴다운
- 보관함(선반) 라벨과 연결
- (후순위) 학생이 실/시설 **고장·이상 신고** → 담당교사 큐
### 6.6 실사 (Inventory Check) — P1 (MVP에 가벼운 버전 권장)

- 실 선택 → 예상 목록 생성
- 스캔으로 확인 체크
- 미확인 / 예상외 발견 / 수량 불일치 리포트
- 실사 세션 저장·이어하기 (폰으로 돌아다니며)

### 6.7 바코드·라벨 인쇄 — P0

- QR 기본 (스마트폰 스캔 친화), Code128 옵션
- 라벨 템플릿:
  - 품명, 관리번호, 실/위치, QR, 학교명/로고
- 용지 프리셋: 일반 A4 분할 + **라벨지 규격은 추후 확정** (템플릿만 교체 가능하게)
- 브라우저 인쇄 (별도 드라이버 최소화)
- 보관함/실 라벨도 동일 엔진
- 일괄 인쇄 (선택 항목 N개)
### 6.8 이력·감사 — P0

- 품목/개체별 타임라인 (등록, 이동, 대여, 수리, 폐기)
- 사용자별 활동 로그
- 단순 되돌리기(잘못된 출고 취소) — 권한 있는 사용자

### 6.9 AI 도우미 — P1 (차별점, 초기부터 설계에 자리 확보)

목적: **재고 입력·정리·의사결정 보조**. 환각으로 재고를 바꾸지 않음.

**프로바이더 (설정에서 선택)**

| 프로바이더 | 역할 가정 |
|------------|-----------|
| **OpenAI** | 범용 LLM·비전 (사진→초안 등) |
| **Upstage** | 한국어·문서/OCR에 강점 있을 때 |
| **Ollama** | 학교 내부/로컬·키 비용 없이 시험·오프라인에 가까운 운영 |

공통 **AI Provider 인터페이스**로 감싸서 키·엔드포인트·모델명만 바꾸면 되게 한다. API 키는 서버/Functions 쪽에만 둔다.

| 기능 | 설명 | 우선 |
|------|------|------|
| 사진 → 초안 등록 | 장비 사진 올리면 품명·유형·추정 스펙 초안 제안 → 사람이 확정 | P1 |
| 자연어 검색 | “용접실 드릴 중 대여 가능한 거” | P1 |
| 설명/매뉴얼 요약 | 첨부 PDF·이미지 요약, 안전 주의점 추출 | P1 |
| 분류 제안 | 미분류 품목에 카테고리/태그 추천 | P1 |
| 실사·부족 리포트 문장화 | 실사 결과를 인수인계용 문장으로 | P2 |
| 구매 후보 정리 | 부족 소모품 목록을 발주 메모로 | P2 |

**안전 규칙**

- AI는 제안만; **재고 변경·폐기는 반드시 사용자 확인**
- 학교 데이터 학습 사용 여부·보관 정책을 설정에 명시
- 학생 PII 최소 노출
- 프로바이더 미설정 시 AI 메뉴는 숨기거나 “연결 필요”만 표시 (핵심 재고 기능은 AI 없이 동작)
### 6.10 알림·대시보드 — P1

- 재고 부족 소모품
- 연체 대여
- 수리 중인 장비 목록
- 오늘/이번 주 내 담당 실 이슈
- **텔레그램 봇**: 학교/담당자 채팅(또는 개인 DM)으로 이벤트 푸시
  - 예: 연체  Imp박, 소모품 최소재고 미만, **고장 신고 접수**, 실사 종료 요약
  - 설정: 봇 토큰·채팅 ID·알림 종류 on/off (서버에만 토큰 보관)
### 6.11 가져오기·내보내기 — P1

- 엑셀 템플릿 다운로드/업로드
- 실별·유형별 CSV 내보내기 (보고·백업)
- 에듀파인 자산번호: MVP는 **옵션 수동 필드**
- **에듀파인 파일 동기화(임포트)** — P2:보내기 파일(엑셀/CSV 등) 업로드 → 매칭·신규·충돌 리뷰 후 반영 (실시간 API 연동 아님)

### 6.12 학생·신고 (후순위, 데이터 모델만 열어 둠)

- 내 대여 목록 조회
- 시설/장비 **고장·이상 신고**
  - 대상: **실(Room)** 또는 **장비 개체(Asset Instance)**
  - **대여 중인 개인 장비** 문제는 반드시 장비 개체에 연결 (실만 찍으면 추적 불가)

  - 접수 시 담당교사 텔레그램 알림 (P1 알림과 연동)
- MVP에서는 교사만 쓰기; 스키마에 `reports` 여지 (targetType: room | asset)
### 6.13 비목표 (Out of Scope for v1)

- 회계·감가상각 엔진 (에듀파인 **대체** 금지 — 보조·동기화만)

## 9. 기술 방향 (기획 수준, 확정 아님)

논의를 위한 **가정**이며 개발 착수 시 재합의한다.

| 영역 | 후보 방향 |
|------|-----------|
| 클라이언트 | 반응형 웹 (PWA 후보) |
| 인증 | Firebase Auth (Google) |
| DB/백엔드 | Firebase(Firestore 등) 또는 Auth + 자체 API — **이후 결정** |
| 파일(사진) | Firebase Storage 또는 동등 |
| 바코드 | 브라우저 BarcodeDetector / html5-qrcode 등 |
| 라벨 | 클라이언트 PDF/브라우저 print CSS · 규격 프리셋 교체형 |
| AI | Provider 추상화 → OpenAI / Upstage / Ollama · 서버 프록시 · 제안 전용 |
| 알림 | **Telegram Bot API** (서버/Functions에서 발송) |
| 규모 | 수천 품목·수십 실: 목록은 페이지/커서, 실·상태 인덱스, 검색은 접두/토큰 전략 사전 설계 |
| 배포 | **학교당 1 인스턴스**(Firebase 프로젝트 1개 권장). 설정으로 학교명·도메인·AI 키·텔레그램만 바꿈 |
| 라이선스 | 공개 시 **AGPL-3.0** 제안 (하단 §16) |
### 9.1 단일 학교 + 타교 재사용 전략

의도: 지금은 한 학교만 돌린다. 나중에 다른 학교가 쓰고 싶으면 **우리 SaaS에 가입**이 아니라 **같은 inni를 자기 환경에 올려** 쓰게 한다.

| 해도 됨 (재사용 친화) | 하지 않음 (당분간) |
|----------------------|-------------------|
| 설정 파일/환경변수로 학교명·로고·허용 도메인 | 한 DB에 여러 학교 테넌트 믹스 |
| README·배포 가이드 (Firebase 프로젝트 복제) | 학교 간 과금·구독 포털 |
| 시드 데이터·엑셀 템플릿 표준화 | 중앙 클라우드에 전교 데이터 수집 |
| 코드 오픈 또는 내부 공유 가능한 구조 | 학교 A가 학교 B 재고를 조회 |

→ “멀티테넌트 제품”이 아니라 **이식 가능한 단일 학교 앱**으로 포지셔닝.

보안: 로그인 필수, Storage/DB 규칙, 관리자 승인, 감사 로그.

## 16. 라이선스 제안

학교용·자체 배포형·타교 복제 가능을 전제로 하면 선택지는 대략 셋이다.

| 라이선스 | 타교가 쓰기 | 업체가 가져가 폐쇄형 판매 | 특징 |
|----------|-------------|---------------------------|------|
| **MIT / Apache-2.0** | 쉬움 | 쉬움 (소스 공개 의무 약함) | 채택 장벽 최저 |
| **GPL-3.0** | 가능 (개작 배포 시 소스 공개) | SaaS만 돌리면 회피 여지 | 배포 시 copyleft |
| **AGPL-3.0** ★제안 | 가능 (개작·네트워크 제공 시 소스 공개) | **네트워크로만 서비스해도** 개작 공개 압박 | Part-DB도 AGPL 계열과 결이 맞음 |

**추천: AGPL-3.0**

- inni를 “학교끼리 나누는 현장 도구”로 두고, **개작해서 웹으로 제공하는 쪽은 개선분을 다시 공개**하게 하려는 취지에 맞음
- Firebase/단일 학교 인스턴스와도 잘 맞음 (각 학교가 자기 인스턴스)
- 나중에 “그냥 마음껏 쓰게”로 바꾸면 MIT로 완화하는 건 가능하지만, **AGPL → MIT는 기여자 전원 동의가 필요**하므로 초기에 방향을 정해 두는 편이 낫다

예외적으로 “교육청·업체가 가져다 제품화해도 상관없고 확산이 최우선”이면 **Apache-2.0**이 더 맞다.  
그 경우에도 상표(inni 이름)·학교 로고·시드 데이터는 라이선스와 별도로 명시하는 게 좋다.

의존 라이브러리(Firebase SDK, UI 키트 등)는 각자 라이선스를 따르며, AGPL 본체와 충돌 여부는 공개 전에 한 번 점검한다.
